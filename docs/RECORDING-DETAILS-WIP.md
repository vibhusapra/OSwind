## Canonical user-authored data

The backend introduced in `0c32217` adds `MemoryKind.recordingMetadata` (`recording-metadata`) within the existing canonical `memories` table. It uses the existing native source identity rather than adding a fourteenth canonical sync table. Names are separate user-authored records, not transcript edits or rebuildable-cache-only preferences. Naming preserves the audio IDs, original title/text/timestamps, recording ID and evidence hash. Session targets use exact UTF-8 recording IDs; legacy ungrouped targets use the same exact-evidence-version restriction as recording-scoped Ask.

Name snapshots have an open-store owner and an opaque metadata-row nonce. Editing compares the current snapshot inside a writer transaction and the current settings guard. Deletion/recreation, byte-distinct IDs, concurrent edits, changed/foreign audio and current privacy exclusions refuse stale edits. Multiple definitions are returned as a conflict; the edit API refuses to choose one by date or name. The conflict-management UI is still required.

`recorded_meeting_details` is a derived bounded metadata projection with built-in SQL triggers. It carries per-row revisions and joins the recording change nonce. Repair invalidates prepared metadata without scanning transcripts during installation; historical metadata rebuilding belongs to the later owned worker. Source-cache version 2 and canonical audio identity stay unchanged. Ready archive/revision/publication tests deny canonical payload reads and all SQL writes with a saved name present. The selected-name editing read still hydrates canonical evidence; the archive does not yet display the projected name.

`RecordingCalendarLink` contains the exact occurrence identity, recurrence/date fields, reviewed revision and library binding. It copies no event title, attendees, description or join URL. It is data, not Calendar permission, proof of attendance or execution authority. The live provider/access/selection/library/privacy/source checks and historical resolver must be implemented before a user-facing link action.

## Typed transport in development

`SyncRecordingDetails` carries the source-origin session token or an exact audio wire-version reference. Imported clip IDs are remapped through the admitted canonical owner and retained original. Missing originals never select current text, similar titles or dates. Source graph admission, both original-evidence stores and retirement/peer erasure traverse the new exact reference; self-references and non-audio parents refuse. Incoming names require an already admitted audio owner. Causal delivery can queue a later name and replay both operations when the earlier audio arrives, without creating a source from a dependency body or echoing peer writes.

The optional field is absent from existing wire kinds, and metadata requires the new source subtype. Wrong kinds, missing details, captured assets and unknown details versions refuse. Calendar references remain bound data after transport, with no event contents or implied Calendar authorization. Both native-row and portable-body service policy scan calendar identifier strings for secret patterns as well as checking the authored name.

At source `e3bb845`, the temporary blanket transport refusal was removed, while unavailable or ambiguous exact originals still refused export. The current prototype below adds explicit unavailable projections. Durable affiliation through real rename, retained-original recovery and restored catalog lifetimes still needs implementation and controls. A namespace or matching hash alone must never manufacture authority. This is not complete transport acceptance.

## Current affiliation prototype — known rename failure

Source `c0668cb` uses the previously admitted metadata projection checksum to prove a native scope's original wire affiliation. This preserves its exact reference through favorite changes, including native model provenance that differs from the portable representation. Checked missing owners or unavailable source revisions can instead produce an explicit unavailable link while preserving the native authored metadata and allowing unrelated publication. Policy, integrity, identity and cancellation failures are not converted to unavailable. Reentrant root/target edits refuse and roll back. A later matching audio hash cannot revive a previously unavailable affiliation.

This proof is not durable through every native edit. The real name-edit API intentionally purges old metadata wire-cache content. After an equivalent audio wire change, a subsequent real rename loses its original wire reference. The current ten-control selection has **nine passes / one failed method / zero skips or unexpected errors**. The failure concerns the exact wire version of the same canonical audio/evidence; it does not establish that different transcript contents were selected. The failed control remains in the branch. A bounded affiliation store containing only the owner/scope/reference or unavailable state is the next design to implement and verify; retaining an old private name to keep a link would violate cache-purge behavior.

Native transcript replacement intentionally purges an old cached audio body. The original retention probe tried to reuse that lost body and was too broad. Current separate controls verify exact affiliation after a favorite-only change with normalized provenance, and explicit unavailability after transcript replacement, without reconstructing the lost source. Both pass. Actual retained-history recovery, native rename durability, restore/lifetime, schema and erasure integration still require controls before transport acceptance.
