# Signed pairing and transport — internal sync WIP

The current core can create an owner-signed device membership, admit a joining Mac's signed public request, deliver the group key only to that request's separate agreement key and exchange signed native operations through a v3 encrypted folder. The app takes lifetime ownership of asynchronous setup before it may touch native storage. This remains internal: there is no public create/join constructor, persisted Keychain enrollment or complete user pairing flow. F059 stays TODO.

Device signing and key agreement use distinct CryptoKit Curve25519 keys generated on the joining side. A signed request binds its replica, request nonce, device name, public keys and exact capability floor. Requests expire after ten minutes; up to one minute of future clock skew is accepted. Device names have a byte limit and reject controls and bidi overrides. Parsing is bounded and canonical, including unknown-field refusal.

A separate root signing key issues the membership certificate. Its signature binds group, epoch, owner, revision, predecessor digest, devices and capabilities. The certificate admits at most 64 distinct device identities, signing keys, agreement keys and request digests. Exact repeated admission is idempotent; a second identity using the same private keys is refused. An explicit successor check requires one addition, preservation of all prior entries and the exact predecessor digest. This format adds members; it does not implement revocation, key rotation, persisted membership freshness or a root-history transparency service.

The owner must admit the exact request before producing a response. Each response uses fresh ephemeral X25519 agreement and AES-GCM. The encrypted payload contains the group key and signed membership. The root also signs the response context and ciphertext, so possession of a public request or an old public certificate cannot authorize a substitute encryption key. The recipient must supply the root fingerprint learned from its trusted Mac, verify the exact request digest and check the included member before accepting. Private key/authority/pending/joined values redact descriptions and Mirror. No actual user Keychain or clipboard is used by these components. Replaying the same valid response to the same still-pending request is not a durable one-time-enrollment check; consumption belongs to the unfinished enrollment owner.

A signed folder installs only `space-v3`, pins the root and capability floor in its authenticated marker, refuses opening a v2 folder as v3 and refuses a coexisting v2 marker on open. V2 remains the existing internal transport and private inbox format. V3 author packets bind group, epoch, replica, purpose, opaque descriptor digest and exact body. Operations, collection controls, mutable heads and supersession proofs require the matching member's signing key. Holding the group AEAD key cannot impersonate another device. Content chunks retain their full byte bound and are authenticated through signed immutable hash/length references. Per-device signing does not protect availability against a withholding or destructive provider.

A supersession proof signed by device A can authenticate A's own embedded replacement when that immutable packet is unavailable. It cannot substitute an embedded copy for device B's missing signature. Cross-device replacement waits for B's actual signed operation. Existing causal, deletion, policy and native citation admission still apply.

`PersonalSyncModel.prepare` owns the setup task before invoking its operation. Retirement and cancellation retain and join it even if it ignores cancellation and returns a session late. That late session stops and closes its private inbox before SQLite close or vault detach. Live adoption rechecks exact MemoryStore identity, library admission, lock and retirement state, then preserves processing/network intent. Duplicate setup is refused while cleanup remains active; overlapping drains join actual work. An abandoned UI owner is not retained by the pending operation and still stops a returned late session. The setup operation remains responsible for partially constructed resources before returning a session; this API does not grant enrollment authority or roll back persisted enrollment state.

## Remaining delivery gates

Persistence must distinguish macOS Keychain implementations. Apple documents that data-protection access depends on the host executable's provisioned signing authority, while macOS accessibility attributes require data-protection or synchronizable storage. A login-Keychain flag alone is insufficient evidence for device-only protection. This component establishes no actual user-Keychain, hardware-binding or signed-app credential acceptance. [Apple TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains), [accessibility requirements](https://developer.apple.com/documentation/security/ksecattraccessible).
