# Membership refresh — WIP

Complete device lifecycle remains the delivery target: adding devices after delivery starts, offline peers accepting a verified membership history, removal/revocation and key rotation, durable native/Keychain recovery, native controls and real devices/providers. F059 remains TODO. The public pairing reservation refusal stays in place until the complete transition can be applied safely.

The first implementation supplies an internal addition-history proof. Canonical pages contain a root-signed base certificate and contiguous signed successors, bounded to 98,304 bytes. The exact trusted certificate must occur on the path. Overlapping pages and exact retries are accepted; a signed fork at the same revision, missing step, stale-only page, unknown root/group/epoch, tampering and noncanonical input refuse. Pagination validates the whole supplied path before choosing a fitting prefix, so corruption in an unsent tail is not hidden. Existing device keys and the group secret remain unchanged. This is neither revocation nor an epoch transition.

A refreshed in-memory joined authority is not a native writer credential. No public activation guard is relaxed, no private Keychain envelope is replaced, and no session reopens using it. Five controls exercise offline multi-addition catch-up and private-material preservation, overlap/retry/rollback, real signed forks/gaps/reordering, malformed/canonical bounds and all 64 members through bounded pages. All five new methods pass in Debug, Thread Sanitizer and optimized builds. Each selection passes 34 methods and skips one unchanged explicit owned-Keychain fixture, with zero failures and no sanitizer race warning. That original fixture is separately covered by the qualified parent source. An initial extra-parenthesis test syntax error and its corrected parse are retained. These are selected development checks, not full native membership lifecycle qualification. See [the development receipt](../benchmarks/sync-membership-refresh-development-v1.json).

Remaining implementation and verification:

- Persist the complete signed public membership history and bind it to the currently anchored owner credential. A provider cannot choose an unrelated signed branch or replace the trusted floor.
- Join the actual session, commands and producers before transition; fence already-open native writers, including the frozen native35 client, before new authority can be used.
- Define the durable transition record across the pairing account, delivery account and native SQL checkpoint. Refuse ordinary service admission during partial/ambiguous commits; reopen must finish the exact saved transition without creating replacement credentials. Fault-test each account compare-and-swap and SQL boundary, cancellation and process death.
- Update peer/cursor/bootstrap state without skipping committed changes, losing privacy holds or resurrecting deletion/collection lifetimes. Exercise a new third library after earlier edits, erasures, restarts and eventual compaction.
- Implement reviewed device removal and root-signed epoch/key rotation, distributing new material only to retained devices. Old provider archives and independent copies cannot be remotely retracted; report that boundary accurately.
- Integrate owner request review, peer membership-update review/status and recovery into the actual native lifecycle. Preserve opt-in reconnect, saved delivery pause, current privacy and quiet post-erasure behavior.
- Qualify three-plus owned libraries, old writers, offline/failing providers, corrupted/forked/rolled-back histories and large graphs before signed-GUI, physical two-Mac/provider and sustained power acceptance.

No broad parity, production Keychain, physical-device or ranking acceptance follows from this protocol step.

The transition needs a separately committed native preparation/fence before private membership handover. A merely cached native checkpoint is insufficient: an already-open native35 connection can retain its old matching SQL proof after an ambiguous external-first commit. Preparation must retain old membership while durably fencing old writers and saving exact recovery intent. Private pairing/delivery authority can advance only after that fence is proven committed. Recovery must preserve legitimate raw local changes made before the fence; it must never repair an ambiguity by replacing device credentials or silently discarding queued work. Native36 compatibility, all writer guards and restricted recovery must be designed and tested together; no schema bump is implemented in this first protocol step.
