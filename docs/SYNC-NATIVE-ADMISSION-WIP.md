# Native sync writer admission and content recovery — WIP

An internal service can now explicitly install enrolled native schema34. Ordinary unconfigured and pairing-preview libraries remain schema33. Content tables are unchanged. This installation is not exposed as public transfer activation; F059 stays TODO.

Every current native connection registers a small connection-owned SQLite capability, initially false. Persistent BEFORE INSERT/UPDATE/DELETE guards cover ordinary main native tables, excluding SQLite internals and virtual/shadow tables. Enrollment admits only its verified owning connection. Older already-open clients lack the function; current clients opened before enrollment keep a false capability. Both refuse subsequent guarded writes, including statements prepared before enrollment. Older clients reopening schema34 refuse the newer native version.

Reopening an enrolled library verifies its original external delivery account, checkpoint token, membership, Mac/installation, physical library/vault and publication lifetime before constructor migrations. It serializes with the delivery transaction so another owner's external-save-before-COMMIT interval is not mistaken for rollback. A pairing reservation also survives restoring a schema33 database from before enrollment; that reservation is checked before migrations and cannot allocate a fresh zero floor. Missing credentials require recovery. No credential enumeration or protection-tier fallback occurs.

Ordinary current CLI/app/MCP writers do not take the delivery owner's exclusive credential lease. Their immutable proof retains no store, service or private key material. Native operations compare the checkpoint and publication lifetime; a changed checkpoint refreshes the external proof under a SQL reservation. The delivery owner passes its already verified committed token directly to its connection, avoiding another Keychain read/decode after each phase. Schema changes revalidate the persistent guards. Ambiguous external save/commit failures permanently deny that installed connection until verified reopen or recovery; cached proof cannot regrant it.

A resumed service acquires and verifies its delivery owner before service installation can replace the native command token. A second preparation therefore refuses without invalidating the current running service.

## Recover existing local content

`backup recover NEW_BACKUP_PATH` requires an explicit source (`--data`, `--vault` or `OSWIND_DATA_DIR`). The app's unavailable-library screen offers **Export recovery backup…** when the existing library is accessible. It uses the ordinary backup format and media/erasure-fence protocol, without sync credentials or migrations. Restore reconstructs allowed content into a new, quiet schema33 library; it does not restore old sync credentials, replicas, pairing or publication metadata.

The recovery connection uses a SQLite authorizer denying data/schema mutations. It retains a read/write handle solely because the backup's final erasure-fence check needs BEGIN IMMEDIATE. It does not expose a MemoryStore to the app. Database and source-root paths are validated, Darwin aliases are kernel-canonicalized before NOFOLLOW open, and absent sources are not created. Existing backup destinations are never replaced. Backup staging and media reservations still create ordinary private work/lock files; this is not a filesystem-immutable forensic reader. Backups remain plaintext.

The app owns recovery progress, cancellation and the source reader. Quit, departure and vault lock cancel and join the operation, including workers delaying cancellation, before storage departure. Late canceled results are not selected as completed backups.
