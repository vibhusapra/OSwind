# Pair Macs — native pairing preview

In Settings → Connect → Pair your Macs, the native app can create an owner group, generate a joining Mac's signed public request, review its exact device name and request fingerprint, return a recipient-encrypted response and verify the owner's independently trusted group fingerprint. Pairing is resumable and uses the dedicated login-Keychain namespace. **Pairing does not start capture, activate a delivery session or transfer memories. F059 remains TODO.**

## Use the preview

1. On the main Mac, choose **Create a group** and name the device.
2. On the other Mac, choose **Join an existing group**. Copy its signed public request to the owner. Compare the request fingerprint displayed on both Macs through a channel you trust.
3. On the owner, review the signed request. Confirm the exact name/fingerprint and approve that reviewed value. Return the encrypted response.
4. On the joining Mac, choose **Verify response**. Paste the encrypted response and enter the fingerprint displayed on the owner's screen through your trusted channel. Verify and save.
5. The resulting **Device paired** screen means the device identity is saved. Delivery configuration and activation are still unfinished.

Requests expire after ten minutes. Replacing an expired request creates fresh keys, identity and nonce; previously issued responses cannot complete it. If the owner already admitted the old request, its unused membership remains in the addition-only certificate until group recovery/rotation is implemented. Re-approving the same current request is idempotent and can generate another encrypted response when copying failed.

**Retire local pairing keys** writes a keyless Keychain tombstone. It does not revoke membership on another Mac, delete memories or permit reuse of the old device identity. The preview has no recovery or rotation UI yet.

## Persistence and failure boundaries

The public `PersonalSyncPairing` core owner returns only public status, immutable reviewed requests and encrypted responses. Private signing, agreement, group and owner material is explicitly serialized only into a bounded Keychain envelope. SQLite holds an immutable nonsecret account/protection handle and a dedicated pairing-library lifetime. It never stores pairing keys, encrypted-response payloads, device names or pending request bodies.

A per-credential cross-process lease covers the whole owner lifetime. The native handle/lifetime reservation commits with `synchronous=FULL` before credential creation. A crash, denied credential creation or missing item leaves that exact handle for recovery; reopening never silently creates replacement keys. This is a conservative failure boundary, not an atomic SQLite/Keychain transaction or completed recovery flow.

Pairing checks the installation identity, locally hashed Mac identifier, capture scope, native filesystem volume/directory inode and its dedicated lifetime. Encrypted libraries additionally pin their host volume and outer package/sparsebundle identities. The raw Mac identifier is not saved or logged. Whole-library native local/group wipe markers retire the pairing lifetime; individual source deletion preserves it. Lifetime hooks are checked before reuse. This is software admission, not Secure Enclave or hardware device-only protection.

Membership updates persist before the owner returns an encrypted response. Acceptance replaces pending keys with the verified joined material and a consumed request digest in Keychain. Reopening or restoring an older native database cannot turn that external paired state back into a pending request. Retirement removes private material while preserving the nonsecret consumed-state record externally. These checks protect this pairing lifecycle; they do not yet establish outbound sequence or incoming receipt rollback protection for an active delivery session.

`PersonalSyncModel` takes ownership before a worker enters SQLite or Keychain work. Quit, library switch, wipe and encrypted lock join that tracked operation before storage departure. Cancellation is advisory: a late credential commit can persist, and the next load resumes its saved identity rather than pretending cancellation rolled it back. Wrong-library factories are rejected before performing any pairing mutation. The native sheet bounds pasted input, requires explicit fingerprint comparison and marks copied public/encrypted messages concealed/transient/autogenerated so compatible clipboard observers ignore them.

The preview deliberately selects login-Keychain storage. Data-protection storage remains a distinct backend; its XCTest-host capability result does not establish production application entitlements. No silent downgrade, plaintext fallback, existing credential enumeration or automatic external message is used. Ad-hoc signing/Keychain access across actual app rebuilds remains a live acceptance gate.

## Qualification scope

Source `9ad15a0` and the [qualification receipt](../benchmarks/sync-pairing-preview-v1.json) bind [all 1,478 tracked inputs](../benchmarks/sync-pairing-preview-inputs-v1.json). Full debug **2,389 passed / 139 skipped**; affected Thread Sanitizer **134 passed / 10 skipped**; affected optimized **134 passed / 10 skipped**; explicit owned Keychain/render **28 passed without skips**. All 22 new regular methods pass each software mode; no race warning appears. The explicit native run includes a real owned login-Keychain pairing/reopen/one-time consumption/retirement round trip and native light/dark layout captures. The broad run's skips include opt-in native fixtures and five prior-binary compatibility cases whose frozen executables were not supplied; earlier successful compatibility evidence remains separate. Eighteen captures cover initial setup, owner, request, response entry, exact review, encrypted response, paired, retired and error states. OCR must find the expected state-specific text, so a blank scroll area cannot pass merely by producing an image. These are offscreen owned native views, not evidence of a person completing setup in a signed distribution app or two physical Macs exchanging memories.

Earlier development failures are retained: Swift fixture compilation mistakes; a snapshot harness that triggered real sheet-disappearance cleanup; an ImageRenderer capture that omitted the scroll area despite passing a file-size check; and an OCR-verified review screen whose approval button was below the visible area. The final screen separates request/review/response and request/verification stages so the action stays visible.

## Remaining work

- Delivery credential phases and verified session factory; shared-folder choice and provider access.
- External writer sequence/digest and incoming head/receipt/collection checkpoints before any provider writes; enrolled writer admission, including already-open older clients.
- Binding renewal only after exact native local/received erase completion and physical cleanup; no causal/deletion-history reset to reconnect.
- Membership refresh on already-paired Macs, recovery, revocation and key rotation.
- Offline backpressure, durable raw-queue admission, cold-provider behavior, bounded resumable large graphs and selective spool/backup semantics.
- Actual signed-app Keychain and setup interactions, physical two-Mac/provider transfer, sustained power and notarized distribution. Whole-product feature parity and top-three ranking remain unproven.
